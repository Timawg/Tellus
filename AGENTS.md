# Tellus development instructions

These instructions apply throughout the repository. Tellus is a SwiftUI app with a MapKit bridge. Build the `Tellus` scheme in `Tellus.xcodeproj`. The app supports iOS and iPadOS 17.5 and later. Local development uses Xcode 26 or later, CI uses the `xcode-27` runner, and the project currently builds in Swift 5 language mode. Treat changes to language mode, default actor isolation, deployment targets, and CI toolchains as separate migrations.

## Design and architecture

- Apply SOLID at boundaries. Give each type one clear responsibility. Extend features through existing seams when they fit. Keep protocols narrow, and preserve the contract for every implementation, including failures and cancellation. Inject dependencies where callers need interchangeable implementations or tests need to control an external boundary.
- Wire production dependencies in `TellusApp` and `MainMapServices`. Reuse `NetworkServiceProtocol`, `Service`, `Endpoint`, and `MapPreferencesStore` where they fit. Use concrete types and composition for straightforward cases. Add a protocol, layer, or dependency only when it solves a concrete problem.
- Keep SwiftUI views focused on presentation and user interaction. Put workflow and selection state in view models, transport and provider decoding in services, and reusable calculations in models or focused helpers. Keep UIKit and MapKit integration in the existing representable, coordinator, and layer types.
- Give each feature one owner for its state and task lifetime. When adding an independently managed feature to a large view or view model, keep its state and dependencies together in a focused type. Keep calculations deterministic by passing their inputs explicitly. Read the clock, locale, and storage at the boundary that owns them.
- Make the smallest coherent change that works through the normal app entry point. Preserve existing behavior, persisted keys, and stored data unless the task changes them. Provide a migration when a stored representation changes. Check target membership in `Tellus.xcodeproj` when adding or moving source files or resources.
- Review new dependencies for maintenance, licensing, and deployment support. Commit the Xcode project's `Package.resolved` when dependency resolution changes intentionally. Record the reason for non-obvious decisions and invariants close to the code.

## Swift and concurrency

- Write all new and modified Swift code, including tests, to satisfy Swift 6 language rules and build with the project's current Swift 5 settings. Verify affected targets with the command-line build setting `SWIFT_STRICT_CONCURRENCY=complete`. Also build with `SWIFT_VERSION=6.0` when the affected targets can compile in that mode. Fix Swift 6 diagnostics in the code you change and report any unrelated diagnostics that prevent verification.
- Use `async`/`await` for asynchronous work. Prefer structured concurrency with `async let` for a fixed set of independent operations and task groups for a dynamic set. Use SwiftUI `.task(id:)` for work tied to a view or selection. Keep a cancellable handle for long-lived work such as polling, and stop it when its owner or active layer goes away.
- Keep UI state and view model mutations on `@MainActor`, and use `@Observable` for new observable state where it fits. Isolate shared mutable caches and service state in actors. Pass immutable `Sendable` values across isolation boundaries and use `@Sendable` for closures that cross them.
- Check the active Swift language mode and concurrency settings before using newer isolation features. Consider `@concurrent` for CPU-heavy parsing or geometry that must leave the caller's actor, and `nonisolated(nonsending)` when caller isolation is intentional. An `async` function can still execute on the main actor. Verify availability and test the boundary you change. [Swift concurrency migration guide](https://www.swift.org/migration/documentation/swift-6-concurrency-migration-guide/) · [Swift async function isolation](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0461-async-function-isolation.md)
- For a Swift 6 migration, first audit with `SWIFT_STRICT_CONCURRENCY=complete` in Swift 5 mode. Resolve isolation and sendability diagnostics in the app and test targets before switching language mode. Document any temporary compatibility annotations and the conditions for removing them. [Swift migration strategy](https://www.swift.org/migration/documentation/swift-6-concurrency-migration-guide/migrationstrategy/)
- Recheck cancellation and the active selection after suspension before publishing results. Keep actor state consistent across `await`, coalesce duplicate requests where it matters, and keep retries bounded. Treat cancellation as routine cleanup. Document the safety invariant for any necessary `@unchecked Sendable` and the lifetime of any necessary detached task.
- Prefer small value types, explicit names, and typed errors at boundaries where callers need to distinguish failure cases. Use `FormatStyle` for user-facing numbers, dates, and currencies. Follow the style of the surrounding code and keep formatting changes scoped to the work.

## Data and interface behavior

- For a new or changed provider, verify the official endpoint, commercial reuse terms, attribution requirements, and rate limits. Keep credentials out of source and logs. Reuse existing cache and retry behavior where appropriate, and respect `Retry-After` when supplied.
- Keep provider payloads at the service boundary. Validate them before mapping into domain models, and define how missing or unknown fields affect the feature. Key caches by the inputs that affect the result, and keep the last usable entry when a refresh fails if the feature can display it as stale.
- Present the source, observation date or year, geographic scope, and units alongside figures where they affect interpretation. Label estimates and forecasts. Compare figures with compatible units, definitions, and observation periods. Handle loading, unavailable data, stale results, and failures distinctly. Keep the README's data credits current when a provider changes.
- Test map work at the relevant zoom levels and layer combinations. Keep expensive parsing and geometry preparation off the main actor, reuse overlays when their inputs are stable, and keep renderer state safe for concurrent drawing. Make controls and data readable with Dynamic Type and VoiceOver, and give map legends labels that make sense without color alone.
- Use `#Preview` with local fixtures for new or substantially changed views when the preview helps review the feature. Show the states users need to distinguish, such as empty and failed loads, and keep previews independent of live network access. [Apple's SwiftUI preview guidance](https://developer.apple.com/documentation/xcode/adding-previews-to-your-interface-files)

## Tests and verification

- Use Swift Testing (`import Testing`, `@Test`, `#expect`, and `#require`) for unit tests in `TellusTests`. Use `#require` when a failed prerequisite should stop the test. Keep XCTest in `TellusUITests` for UI automation and launch performance, which use Apple APIs provided by XCTest. [Apple's Swift Testing migration guidance](https://developer.apple.com/videos/play/wwdc2026/267/)
- Add or update focused tests for meaningful behavior changes and regressions. Use fixtures and injected dependencies for provider responses, persistence, and time where it affects the result. Make tests independent, await explicit signals for async behavior, and use bounded waits. Avoid depending on live services or shared defaults in unit tests.
- Assert observable behavior and use parameterized tests for cases that share the same expectation. Exercise the failure paths the feature relies on, such as sparse provider data, cancellation, or an older response arriving after the user changes selection. Use isolated fixtures and reserve `.serialized` for tests with an unavoidable shared resource. [Apple's parameterized test guidance](https://developer.apple.com/documentation/testing/parameterizedtesting)
- Run the tests relevant to the change. Use **Product → Test** or run the `Tellus` scheme with `xcodebuild` and an available simulator. For unit-only work, use `-only-testing:TellusTests`. Run the full scheme for changes that affect UI automation or the CI test workflow. Discover simulator IDs with `xcodebuild -project Tellus.xcodeproj -scheme Tellus -showdestinations`, then use `-destination 'platform=iOS Simulator,id=<UUID>'`.
- When changing CI, keep the hosted test command reproducible locally. Preserve simulator setup diagnostics and retain an `.xcresult` bundle when a test run fails so failures can be inspected after the runner exits.
- Check `git diff --check`, review target and resource changes, and report what you verified and any checks that could not run. Keep unrelated workspace edits out of the change.
